# 开发看板维护规则

[ISAtlas Roadmap](https://github.com/users/noionion/projects/5) 用于维护功能规划、开发进度，以及需要跟踪的 Bug。看板关联 `noionion/ISAtlas` 仓库，公开供访客只读查看；编辑权限仅授予维护者。仓库 Issues 用于接收公开反馈。

## 条目放在哪里

| 内容 | 维护位置 |
| --- | --- |
| 维护者已确定或准备评估的功能 | Project 草稿条目 |
| 暂时不做、保留以后考虑的功能 | Project 草稿条目，状态为“暂缓” |
| 用户功能建议、问题反馈与需要追踪的 Bug | 仓库 Issue，按需加入看板 |
| 需要独立讨论、依赖关系或原生父子任务的事项 | 正式 Issue，按需加入看板 |

规划默认使用草稿，不为每个想法创建仓库 Issue。同一个 Issue 加入看板后直接维护原条目，避免复制出另一份规划。

## 大功能与子功能

每个大功能保留一个草稿，子功能写在正文的勾选任务清单中，不另外创建一排子功能卡片。每项记录简短说明与验收标准；跨功能依赖写在正文末尾。

```markdown
简要说明要解决的问题与功能范围。

状态：暂缓。尚未安排发布版本。

## 子功能任务清单

- [ ] **子功能名称**（暂缓）

  简短说明预期行为。

  验收标准：能够明确判断该项是否完成。

## 依赖与实施说明

记录前置条件、共用能力和需要明确的边界。
```

草稿任务清单没有原生父子 Issue 关系，子项状态由正文维护。总功能进入“进行中”时，尚未开始的子项仍标为“待开发”；验证通过后再勾选对应任务。总功能暂缓时，可将未完成子项一并标为“暂缓”，并说明原因。

当某个子功能需要独立讨论、单独排期或关联阻塞关系时，再拆成独立草稿或正式 Issue，并在总功能中引用它；拆分前保留原有说明与验收标准。

## 状态流转

| 状态 | 含义 |
| --- | --- |
| 待评估 | 范围、价值或实现方式尚待确认 |
| 暂缓 | 保留规划，当前不投入开发 |
| 待开发 | 已决定支持，等待开始 |
| 进行中 | 当前推进的功能，可包含尚未开始的子任务 |
| 待验证 | 已实现，等待必要的功能验证或复核 |
| 已完成 | 已满足验收标准，并通过相应验证 |

通常按“待评估 → 待开发 → 进行中 → 待验证 → 已完成”推进。未准备推进的功能进入“暂缓”，恢复后回到适当状态。

移动条目时同步修改正文中的状态说明，避免卡片状态与正文矛盾。“已完成”表示验证通过；是否已发布、包含在哪个版本中，另行记录。取消或不再支持的规划应说明原因并归档，不标为“已完成”。

## 字段与视图

- `Status`：功能当前状态。
- `所属功能`：功能归类；正式 Issue 加入看板时，可关联到相应的大功能名称。
- `条目类型`：总功能使用“功能”。现有“子功能”选项仅在确需拆出独立条目时使用。
- “功能看板”：按状态查看和推进工作。
- “功能清单”：集中查看条目及字段。

暂缓条目不承诺发布版本。决定排期后，草稿在正文记录目标版本；正式 Issue 可使用版本 Milestone。每次准备发版时复核待开发事项、验收结果和版本范围，避免将候选想法当作交付承诺。

## Issue、Bug 与代码关联

Bug 记录复现步骤、预期与实际表现、应用版本及必要的环境信息。功能建议说明使用场景和希望解决的问题；已有相同规划时，在 Issue 与看板草稿之间互相引用，不重复维护需求正文。

正式 Issue 使用 `bug`、`enhancement`、`documentation` 等标签分类，模块标签按需增加。进度由看板状态维护，避免再添加一套重复的进度标签。

| 关联方式 | 使用场景 |
| --- | --- |
| 正文引用 Issue 链接或 `#编号` | 记录相关反馈、实现或问题 |
| 原生父 Issue / 子 Issue | 拆分需要独立跟踪的正式 Issue |
| `Blocked by` / `Blocking` | 表示必须先完成的前置事项 |
| PR 或提交中的 `Refs #编号` | 关联实现，保留验证后关闭的时机 |

原生父子关系和阻塞关系用于正式 Issue，Project 草稿通过正文清单与链接维护关系。

仓库当前默认分支为 `dev`。`Fixes #编号` 等关闭关键字会在相关提交进入默认分支时关闭 Issue；若还需等待验证，使用普通引用，并在验证通过后关闭。默认分支调整后应同步复核这一约定。

## 维护边界

创建或调整规划不等于实施代码，也不触发应用发版。发版仍遵循仓库版本与 Release 规则。

公开 Issue、文档和看板内容仅使用可公开的信息，不写入凭据、签名文件位置或企业内部 CSR / 指令数据。私有数据包相关需求可以记录通用功能边界，具体内部数据不附在规划条目中。
